# 日统计直写国内供应商编码

**目标：** 生成商品分店日统计时，把国内货的本地供应商 `200` 解析成具体国内供应商编码，直接写进 `ProductStoreDailySalesStatistic.SupplierCode`。国内供应商口径的统计不再依赖 POSM 的 `posm_product_supplier_mapping` 是否同步及时，归属按最后一次重算时的主数据固定下来。

**背景：** 映射增量同步从 2026-07-06 起静默漏同步两个半月（PR #255 已修），期间 2949 个新商品没有映射行，2026-09-19 当天约 17% 的国内货销售额还原不出国内供应商。

下文「国内编码族」指 `200` 加上全部国内供应商编码；「直写行」指 SupplierCode 已是国内供应商编码的日统计行。

## 现状（2026-09-21 调研）

- 日统计 SupplierCode 直接取收银明细行（POSM `sales_order_detail.SupplierCode`、HBSales `B供应商ID`），为空才用映射的 `LocalSupplierCode` 兜底。国内货写的都是 `200`，约占销售额 40–45%。
- 读取侧已经是半成品：提交 ee850f7b2（2026-09-06）把看板服务二十多处、拆分表构建器（`isDirectChina`）、销售明细投影都做成了「旧 200 + 直写行」两种都认，注释写明「新日统计直接把中国供应商编码写入 SupplierCode」。写入侧一直没切，生产里直写行为 0。
- 订货助手不受影响：四个入口都先过 `EnsureSupplierEnabled`，只接受配置了供应商网站的澳洲供应商，`200` 走不到查日统计那一步。

## 已确认的决定

| 项 | 决定 | 依据 |
|---|---|---|
| 解析来源 | 主数据：未删除 `WarehouseProduct` 关联未删除 `DomesticProduct` 的 `SupplierCode`，且编码存在于 `ChinaSupplier`；解析不出保持 `200` | 抽样 2026-09-19、2025-11-15 两天，主数据与映射零冲突且是超集；411 个国内商品供应商编码全部在 `ChinaSupplier` 里；本地与国内两套编码零重叠 |
| 归属口径 | 每次重算都重新解析，季度结束后冻结 | `WarehouseProductChangeHistory` 自 2026-08-12 起 1285 次国内供应商变更全是新建关系，A 改 B 为 0；晚绑定才是常态 |
| 历史回填 | 不回填。旧日期保持「200 + 映射」，读取侧照常还原 | 历史的当时归属无从还原，回填只能盖上今天的主数据，与映射现在给出的结果相同 |
| 开关时间 | 2026-09-30 季度任务之后 | 季度任务 2026-07-06 才加入，9-30 是首次运行，一次 92 天，不再叠新变量 |

## 分期

### PR-A 读取侧（#261，已合并）

生产现在没有直写行，上线后行为不变，可单独发布。

1. 新增 `ChinaSupplierCodeFamily`：读取全部国内供应商编码（含停用、软删除），生成顺序固定的过滤列表。
2. 热销榜三处（榜单、分店明细、条码品名）、货柜分摊销售两处，由只认 `200` 改为按国内编码族过滤。
3. 紧凑销售看板立方体：直写行不依赖映射，映射为空不再直接返回空看板；逐行还原国内供应商后再合并回「每个门店×商品一格」；同一商品解析出多个编码时取最近销售日的归属。
4. 国内编码集合统一为包含软删除：`GetChinaSupplierCodeSetAsync`、拆分表构建服务。否则供应商日后被软删除，它的历史直写销售会在澳洲侧变成一个普通供应商。旧 200 行不受影响，它们的编码来自映射种子，本来就不看删除标记。

### PR-B 写入侧（配置开关，默认关）

开关：`SalesStatistics:WriteDirectChinaSupplierCode`，compose 里由服务器 `.env` 的 `SALES_STATISTICS_WRITE_DIRECT_CHINA_SUPPLIER_CODE` 注入，默认 `false`。

- 读取器 `SalesStatisticsProductStoreDailySourceReader.LoadAsync`：国内供应商编码目录总是加载（折叠匹配要用，与开关无关）；开关打开时才用一条固定文本的查询读出「商品 → 国内供应商编码」。原始明细行不改动，成本回填的来源哈希和证据都基于它。
- 聚合器 `SalesStatisticsProductStoreDailyBuilder`：国内货的 `200` 改写成解析出的国内编码；解析不出的、编码不在国内供应商目录里的、仓库商品或国内商品已软删除的，都保持 `200`。
- 成本回填不解析归属：它重建的行只用来取成本，靠折叠匹配和库内行配对，回填只改成本列。

`SupplierCode` 在日统计表里同时是主键的一部分和成本匹配键，下面三处必须和写入切换同一个发布：

| 位置 | 问题 | 做法 |
|---|---|---|
| `SalesStatisticsProductStoreDailyBuilder` 成本解析 | 按「供应商+商品」匹配 `StoreRetailPrice`，国内货在那里记的是 `200`，约 78% 的 200 行成本来自它 | 输出行写国内编码，成本解析仍用 `200` |
| `PreserveHistoricalCostSnapshots` 与取成本锁的判断 | 按 (Date, Branch, SupplierCode, Product) 找旧行；键一变，历史成本快照被当前进价覆盖，无法恢复。所有历史日期重算都经过这里 | 精确键找不到时，国内编码族内按「日期 + 分店 + 商品」再找一次 |
| 成本回填的重建行配对与 `Propose` 的销售事实比较 | 都按含 SupplierCode 的键；对不上时提案因「来源缺失」或「来源事实不一致」丢掉 | 同上，并把重建行的编码对齐到库内行 |

折叠匹配只在编码属于国内编码族时才生效，澳洲供应商之间、澳洲与国内之间不折叠：它们在分店价格表里是不同的成本身份。

测试：开关关闭时输出与改造前一致；开关打开后成本仍取按 `200` 登记的分店进价；历史日期在「200 变直写」「直写变另一编码」「直写变回 200」三种过渡下成本快照都不变；当天营业中快照入口同样生效。对照实验：去掉折叠匹配，历史成本 2 被当前进价 3 覆盖；让成本解析用写出的编码，成本来源从分店进价掉到商品进价。

### 上线

1. PR-A、PR-B 上线，开关保持关闭。
2. 9-30 季度任务跑完后，在服务器 `.env` 里设 `SALES_STATISTICS_WRITE_DIRECT_CHINA_SUPPLIER_CODE=true` 并重建 API 容器。例行重算会把当天、昨天、之后第 2 到 6 天，以及之后每周、每月、每季任务覆盖的日期写成直写行；更早的日期保持旧方式。
3. 次日核对：澳洲侧 `200` 合计不变；国内侧合计等于直写行加旧行；前 6 天成本合计不变。
4. 回退：关开关。已写成直写行的日期不用处理，读取侧两种都认。

## 已知影响

- 被改写成直写行的日期，对应的成本回填批次不能再回滚（已应用 496 天）。
- `SupplierCode` 参与版本哈希，被改写的日期版本必变；正常写入路径会在同一事务里重发拆分表和销售明细投影。
- 旧日期继续靠映射还原，PR #255 与一次全量映射同步仍然需要。

## 不做

- 给日统计表新增国内编码列：不动主键和成本键，但二十多处已兼容两种行的读取代码要重写才受益。
- `SupplierSalesStatistic`、`StoreSupplierSalesDetail`：从收银明细加映射独立生成，不读日统计，没有前端调用方，保持不动。
- 历史改写工具：以后想让统计彻底脱离映射时再做，只改归属、不重算销售，范围约 350 万行（估算）。
