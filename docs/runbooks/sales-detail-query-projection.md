# 销售明细关键词查询投影

销售明细关键词查询先通过历史名称、条码和实时商品目录找候选商品，再回读候选商品的完整日事实。供应商、分店及分母从日投影合并，查询各栏在同一个 SQL Server SNAPSHOT 内读取。关键词仍只影响筛选汇总和商品栏。

多个关键词先用最长词建立必要候选，其余词仅检查候选商品的当前资料，最终仍逐词执行 AND 筛选。候选按规范商品码选中后，展开该商品的全部原始码形式，保留带空格编码所参与的跨日聚合。仓库供应商共同使用原始码 `200`；没有重复映射时，供应商命中会通过已核验的每日映射缩到商品码，避免读取整个仓库的明细。选中商品会独立进入候选，保持左两栏联动口径。

没有供应商整段事实待读时，其余词的商品资料匹配会提前到事实读取之前。如果某个词在本期及同比涉及的供应商代码、名称和中国供应商目录中均没有命中，再用商品历史别名及当前资料缩小候选；存在供应商命中就跳过该词的预筛。预筛按规范码整体保留或排除所有原始码形式，并始终保留选中商品，最终仍读取保留商品的完整事实。

当前资料、规范商品码或选中商品命中时，首次扫描已经包含该规范码的全部原始形式；只有历史名称或条码单独命中的商品，才额外展开其他原始形式。候选商品不超过 2048 个时，回读只取报表必需的 11 列并按商品码查询；更广泛的候选由 SQL 优化器选择读取方式。多词投影的目录、聚合和筛选语句设置 `MAXDOP 4`，不改变数据库全局配置。状态传输只包含本报表实际消费的 `ProductStoreDaily`，对外状态与缓存版本仍由相同的发布记录计算。

## 数据与发布身份

- `SalesDetailQueryDaily`：日期、原始授权门店、规范化门店、原始及解析后的供应商维度金额、数量、成本计数和商品范围。
- `SalesDetailQueryProductAlias`：历史商品码、名称及条码候选词典；只扩大候选，最终仍按原查询跨日 `MAX` 名称及多关键词条件过滤。
- `SalesDetailQueryProjectionState`：日事实版本、聚合时间、任务身份及映射签名。
- `SalesDetailQueryMappingUse`：每日实际销售的仓库商品与当时中国供应商映射，跨门店去重。

日事实成功发布时，writer 在同一事务内刷新派生表，最后提交。`ProductStoreDaily=Failed` 但保留 `LastAggregatedAtUtc` 的日期仍有可读商品事实；writer 会在同一事务内为它刷新日投影，报表继续显示原有对账警告。此类日期没有供应商对账版本时，投影使用 `JobId` 与 `LastCheckedAtUtc` 组合的失败身份；重复失败重算后，旧投影会失效。技术性失败且没有聚合时间、未发布或缺少必要身份的日期仍撤销覆盖。批次末尾仅改变 `CompletedAtUtc` 的状态升级不代表事实改变。

映射签名改变时，会检查实际商品映射及供应商分类。无关映射新增不会让历史查询失效；实际影响当前统计的变化、重复映射放大、缺少日期覆盖或发布身份不一致会使整个请求重新走原查询。不能把回退日志当作已满足性能目标。

按月投影也消费相同的失败身份。旧月表的身份不匹配时，查询端从有效日表或该日事实读取；后台月投影任务默认启动一分钟后开始检查，此后每两分钟巡检并先补日表再汇总月份。`Queued` / `Running` 且来源版本为空时保持保守回退，直到有可核验的事实身份。

## 显式迁移与回填

先核对目标服务器、主库、POSM 同实例连接、两个数据库 SNAPSHOT 状态和迁移账本。涉及本功能的主库迁移为：

1. `20260909.002-sales-detail-query-projection`
2. `20260909.003-sales-detail-query-mapping-use`

通用 `--schema=migrate` 会执行该镜像中的全部缺失迁移，必须先确认清单，不能假定只包含本功能。运行时不自动创建派生表。

维护命令使用独立 schema host，不启动 HTTP 或后台任务：

```text
--schema=sales-detail-projection-backfill
--schema=sales-detail-projection-check
```

配置必须明确指定（环境变量以双下划线替代冒号）：

```text
SalesDetailProjection:ExpectedDatabase
SalesDetailProjection:ExpectedServer
SalesDetailProjection:StartDate
SalesDetailProjection:EndDate
```

日期格式为 `yyyy-MM-dd`，含首尾，单次最多 731 天（两年，含闰日）。连接字符串沿用受保护的生产配置，不写进命令行、日志或仓库。

Backfill 按可读的自然日逐日事务提交，完成后在一个 SNAPSHOT 内对整个配置范围做最终检查。可读状态包括 `Fresh`、`ProvisionalFresh`，以及同时有 `LastAggregatedAtUtc`、`LastCheckedAtUtc` 的 `Failed`。Check 枚举所有自然日；缺状态、缺聚合时间、缺对应版本或失败身份、投影不匹配都会失败。回填不能修复源统计的对账差异，不允许通过补造 Fresh 状态绕过门禁。已确认仅缺一天时，将起止日期都限定为该天，避免重写整个历史区间。

发生取消、超时或连接中断后，先执行只读覆盖检查，确认哪些日期已经提交，再限定范围恢复；不要盲目重放整段回填。

## 发布及验收

保留当前 API 镜像及将覆盖的精确源码备份。首次建表时先构建候选镜像、执行显式迁移和常规历史回填，再切换目标 API。修复已有 `Failed` 聚合日时须先切换支持失败身份的新 API，再执行限定日期的回填和覆盖检查；旧 API 不认识该身份。回退旧镜像时无需删除派生表或迁移账本，但旧 API 对含该日期的关键词请求仍可能回退宽事实查询。

验收至少包含：

- 当前区间及同比区间逐日覆盖；当前日期若被旧 API 在回填后重新发布，要再次核验发布身份。
- 真实 SQL Server 下新旧七个结果集或等价对外 DTO，含多词搜索、退货、缺成本、跨日名称和门店权限。
- 真实浏览器从操作到四栏可见的时间，区分第一次查询、重复查询以及回退路径。
- 日志中的 `日投影 True`、实际 HTTP 成功和页面内容；健康检查成功不能替代性能验收。

搜索接口的投影路径每期最多支持 731 天（与页面两年上限一致），更长的后端直接请求由原查询处理。页面放开两年区间后，投影覆盖范围应至少回填到 `2025-01-01`（日统计起点），否则跨过覆盖起点的关键词搜索会回退到原查询的宽事实扫描，长区间可能超过前端 20 秒超时。历史词典按发布追加，用来保证旧名称仍可成为候选；任何后续清理都必须先证明不会遗漏仍受支持的日期。
