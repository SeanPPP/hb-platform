## 0. 结论摘要

这个项目的**代码质量纪律很强，但结构治理缺位**。

具体表现为：新写的代码在正确性细节上做得非常好（金额舍入 101/101 处显式 `AwayFromZero`、远程维护下载的 SHA256 + 定长比较 + 路径遍历防护、`sc.exe` 参数转义、1726 条本地化资源零偏差、零 TODO/FIXME、严格的分层纪律）；但上一份报告点名的结构性问题**一年多来一项未修且全部恶化 50%–160%**，同时在支付关键路径上留下了若干"同一族方法里唯独这一个漏了护栏"的缺口。

本次确认了 6 条严重问题：1 条静默永久丢订单、2 条服务端鉴权、2 条促销算价错误、1 条本地支付仓储零守卫。

本报告结论来自 6 路并行专项审查，**每条严重问题均由主审查者回到源码逐条复核**。每条发现标注了复核状态：

- **[已复核]** — 主审查者亲自读源码验证了全部前提与失败链路

### 1.1 全局 NOLOCK 让订单幂等检查脏读，重试后静默永久丢单 [已复核]

**位置**: `apps/pos-wpf/src/Hbpos.Api/Data/HbposSqlSugarContext.cs:48` + `Services/OrderSyncService.cs:254`

`MoreSettings.IsWithNoLockQuery = true` 全局开启，使订单存在性判断被翻译成 `SELECT TOP 1 1 FROM [sales_order] WITH(NOLOCK)`——表提示覆盖会话隔离级别，事务里的 `Serializable` 对这条读**完全失效**：

```csharp
// OrderSyncService.cs:254，位于 Serializable 事务内
var existing = await db.Queryable<SalesOrder>()
    .AnyAsync(x => x.OrderGuid == plan.Order.OrderGuid, cancellationToken);
```

**失败链路（逐环已验证）**:

1. 客户端 15 秒 HTTP 超时后重试，两个同 `OrderGuid` 请求并发
2. T1 已 `Insertable(plan.Order)` 但事务未提交
3. T2 **脏读**到该行 → 判定 `existing = true` → 返回 `Accepted=true, AlreadySynced=true`
4. 客户端 `OrderUploadService.cs:72` 只判断 `if (!response.Accepted) throw;`——`AlreadySynced` **仅出现在日志字符串里，不参与任何判断**——随即无条件 `MarkSyncedAsync`
5. T1 随后回滚
6. 结果：**POSM 没有这笔订单，本地却标记为 Synced**

**不可恢复性（已验证）**: `GetPendingOrderGuidsAsync` 只取 `Status IN ('Pending','Failed')`（`OrderUploadService.cs:496`），`Synced` 是终态永不重试；全仓**没有任何上传后对账机制**；客户端也从不读 `OrderSyncResponse.Disposition`。这笔销售永远不会被发现。

反向时序（T2 先插）会撞 `sales_order.OrderGuid` 主键而回滚，重试可自愈——**只有脏读方向不可恢复**。该路径在 `Hbpos.Api.Tests` 中完全无测试（测试全用 Fake repository）。

**后果**: 营业额少算、库存不扣减、无任何告警。触发窗口虽窄（INSERT 到 COMMIT 之间），但门店网络不稳时超时重试是常态，且同一事务内还要写明细、支付、挂单关联，窗口可达数百毫秒。

**建议**: 不要全局关闭 `IsWithNoLockQuery`（纯读报表仍受益），改为按语义拆分——幂等判断与额度校验改用裸 SQL 加 `WITH (UPDLOCK, HOLDLOCK)`，或为写事务另建不开 NOLOCK 的 client。同时让客户端区分 `AlreadySynced` 并补一条上传后对账。

### 1.2 两套促销缓存写进同一张表，同一次同步里互相整店删除 [已复核]

**位置**: `apps/pos-wpf/src/Hbpos.Client.Wpf/Services/LocalPromotionRepository.cs:126`、`:331` 与 `LocalCatalogRepository.cs:541`、`:561`，触发于 `LocalCatalogSyncService.cs:383` 与 `:404`

schema 为新促销仓储专门建了 `LocalPromotions` 表（`LocalSchemaService.cs:1525`），但 `LocalPromotionRepository` 的 SQL 实际写的是 catalog 链路的 `LocalPromotionRules`。两者都是"按 StoreCode DELETE 再全量 INSERT"，且**在同一次同步流程中先后执行**：

```
LocalCatalogSyncService.cs:383  catalogRepository.ReplacePromotionRulesAsync()   → DELETE + INSERT LocalPromotionRules
LocalCatalogSyncService.cs:404  promotionRepository.ReplaceStoreRulesAsync()     → DELETE + INSERT LocalPromotionRules  ← 删掉上一步全部
```

代码注释本身说明了设计意图是两套缓存并存——"旧 catalog 促销缓存"与"新 promotion rules 缓存供 POS 端重算使用"——因写错表名而变成后者覆盖前者。

**为什么一直静默**: `LocalPromotionRules` 恰好是 `LocalPromotions` 的**列超集**（多一个可空 `UpdatedAt`），INSERT 不报错。另两处佐证：`LocalPromotions` 在整个 `src/` 下**零读写**（只有一条测试断言它存在）；索引 `IX_LocalPromotions_Store_EffectiveRange` 却建在 `LocalPromotionRules` 上（`LocalSchemaService.cs:1627`）——同一处复制粘贴失误。两个仓储的测试各用独立临时库，碰撞不可见。

**后果**: 收银端经 `ShellCatalogService.cs:221` → `LocalCatalogRepository.LoadPromotionRulesAsync` 读取，拿到的却是 promotion 链路写入的数据。两个接口口径不同——`CatalogService.cs:477` 只返回绑定本门店且有商品明细的规则，`PromotionRuleService.cs:37` 额外包含无门店绑定的总部规则且不过滤空明细。**自动促销按错误的规则集算价**，可能应用本店不该生效的总部促销。

**建议**: 把 `LocalPromotionRepository` 的表名改回 `LocalPromotions` 并同步修正索引。改之前先评估线上已互删多久、受影响门店的促销口径偏差。

### 1.3 服务端收银员权限校验在生产默认整体关闭 [已复核]

**位置**: `apps/pos-wpf/src/Hbpos.Api/Auth/CashierPermissionAuthorization.cs:288`

`Audit` 模式下，对所有不要求票据的策略直接 `context.Succeed(requirement)`，只记一条 Warning 日志。而 `Audit` 正是两处的默认值：

- `src/Hbpos.Api/appsettings.json:24` → `"Mode": "Audit"`
- `docker-compose.hotbargain.yml:47` → `${HBPOS_CASHIER_AUTHORIZATION_MODE:-Audit}`

逐条核对策略注册后确认：26 条 `Cashier.*` 策略中，只有 `RemoteMaintenance`（`AddCashierTicketOnly`，要求收银员票据）和 `DeviceRegistrationReset`（`AddFreshEmployee`，要求新鲜在线票据）两条不受影响。其余全部走通用 `Add()` / `AddAll()`，`RequireCashierTicket` 与 `RequireFreshOnlineTicket` 均为默认 `false`，**包括退货、退款、支付设置、特价标记管理、日结重打、挂单/取单、历史召回**。

**后果**: 持有效设备 Bearer 的终端，无需任何收银员登录即可执行上述敏感操作。服务端的收银员级权限控制形同虚设，真正的权限边界只存在于 WPF 客户端 UI。

**性质**: 代码注释表明这是为兼容存量设备的渐进迁移（"同店既有设备保持 Audit 兼容"），不是疏忽。问题在于迁移停在了"生产默认放行"这一档。

**现状（已确认）**: 存量设备**尚未全部支持票据**，因此不能直接切 `Enforce`——那会让未升级的收银机无法退货、退款、改支付设置。

**建议的过渡路径**:

1. 用现有的 `Cashier authorization audit bypass` Warning 日志按 `store`/`device` 聚合，得出还有多少设备、哪些门店在走 bypass 分支
2. 优先推动这些设备升级到支持票据的客户端版本
3. 加一个**按设备维度**的灰度开关（而非全局 Mode），让已升级设备立即进入 `Enforce`，未升级设备继续 Audit——现有代码已有 `IsAppReviewDeviceAsync()` 这类按设备豁免的先例，可沿用同一机制反向实现
4. bypass 设备清零后再把全局默认切到 `Enforce`

在完成之前，§1.4 的 Square 退款端点归属校验**必须独立修复**——它不依赖收银员票据，是当前唯一能阻断跨店退款的防线。

### 1.4 Square 退款端点没有门店/设备归属校验 [已复核]

**位置**: `apps/pos-wpf/src/Hbpos.Api/Controllers/SquareController.cs:424`（`CreateRefund`）、`:451`（`GetRefund`）

完整校验链只有两步：幂等键格式校验 + 环境与 token 存在性校验，随后把 `PaymentId` 和 `AmountMoney` 原样透传。全链路追踪确认无任何一层兜底：

```
SquareController.CreateRefund:424
  → SquareTerminalBackendService.cs:198  （只取全局 token）
  → SquareTerminalRestClient.cs:368      （payment_id = request.PaymentId，原样发给 Square）
```

三个佐证说明这是漏写而非设计：

1. 同文件 `GetCheckout:235`、`GetPayment:330`、`CancelCheckout:361`、`DismissCheckout:392` **四个同类端点全部**调用了 `ValidateCheckoutDeviceScopeAsync`
2. 该校验函数（`:644`）写得很严格——要求 checkout session 的 `OriginStoreCode`/`OriginDeviceCode` 与认证设备完全一致，连历史无来源行都拒绝，注释写明"不能用当前收银员身份猜测或补写来源"，说明团队清楚这个风险
3. Square token 的 SQL（`SquareTokenService.cs`）只按 `[Environment]` 取、**无门店维度**，是跨店共享的商户 token

**后果**: 任一门店的终端可对**其他门店**的付款发起任意金额的真实退款。结合 §1.3，连收银员身份都不需要。

**建议**: 给这两个端点补 `ValidateCheckoutDeviceScopeAsync`（`GetRefund` 需先按 refundId 反查 payment 归属）。

### 1.5 自动促销把 `UnitWeight` 展开单位重复计价，折扣被放大（少收钱） [已复核] [✅ 已修复]

**位置**: `apps/pos-wpf/src/Hbpos.Client.Wpf/Services/PosCartService.cs:1218`（展开）、`:1236`（求和）

`EnumeratePromotionCartUnits` 按 `quantity × unitWeight` 展开，**每个展开单位都带完整单价**；`ApplyPromotionBundle` 直接 `group.Sum(unit => unit.UnitPrice)` 求 bundle 原价，于是 `UnitWeight > 1` 的商品单价被重复累加，固定总价促销的折扣随之放大。

**同仓库另一套实现是正确的**: `PromotionEvaluationService.cs:209-218` 按 `(Line, SortOrder)` 分组后用 `group.First().UnitPrice` 只计一次，其测试名直接写明语义——`EvaluateAsync_uses_unit_weight_only_for_threshold_count_not_group_total`。

**失败场景**（规则 `applyQuantity=3, fixedPrice=15`）:

| | SKU-A (UnitWeight=2) @12.00 | SKU-B (UnitWeight=1) @6.00 | 组内金额 | 折扣 | 应收 |
|---|---|---|---|---|---|
| 正确 | 12.00 | 6.00 | 18.00 | 3.00 | **15.00** |
| 实际 | 12.00 + 12.00 | 6.00 | 30.00 | 15.00 | **3.00** |

单笔少收 12.00 元。

**可达性（关键，已逐步验证）**: 两套引擎写的是**同一个** `CartLineDiscountSource.Promotion` 折扣字段，后执行者覆盖先执行者。

- 用户操作路径（扫码、改数量）：先同步跑 `PosCartService`（错误值），再由 `PosTerminalViewModel.cs:580` 异步排队 `PromotionEvaluationService` 覆盖为正确值 → **最终正确**
- 非用户操作路径：`ShellCatalogService.cs:229`（目录同步）和远程单品价格刷新只触发 `PosCartService.RefreshAutomaticPromotionDiscounts()`，**不排队 VM 侧重算** → **错误值即最终收款金额**

`UnitWeight` 是后端 `PromotionProduct` 的真实可配置列（`PromotionContracts.cs:17`、`CatalogService.cs:516`）。`PosCartServiceTests` 中没有任何 `UnitWeight > 1` 的用例。

**生产影响（已确认）**: 生产促销规则中当前**不存在** `UnitWeight > 1` 的配置，因此没有实际发生资金损失。但只要后台配置一条权重规则即会触发，属必须修复的地雷。

#### 修复与验证（2026-09-20，PR [#223](https://github.com/SeanPPP/hb-platform/pull/223)）

改动三处，仅限 `PosCartService.cs`：

1. `PromotionCartUnit` 增加 `long SortOrder` 字段，记录该展开单位属于本行第几件实物
2. `EnumeratePromotionCartUnits` 展开时传入 `quantityIndex`
3. `ApplyPromotionBundle` 先按 `(Line, SortOrder)` 折叠成实物单位，再在其上计算组内原价与折扣分摊

语义与 `PromotionEvaluationService.AddGroupDiscount` 的 `(Line, SortOrder)` 分组保持一致——**UnitWeight 只用于凑够 `ApplyQuantity` 的阈值计数，不参与组内金额累加**。

新增回归测试 `PosCartServiceTests.Automatic_fixed_price_uses_unit_weight_only_for_threshold_count_not_group_total`，场景与期望值对齐 `PromotionEvaluationServiceTests` 中的同语义测试。

验证方式：`Hbpos.Client.Tests` 是 `net8.0-windows`，macOS 缺 `Microsoft.WindowsDesktop.App` 无法运行。改为搭建临时 net9.0 宿主直接 link 真实源文件（`PosCartService.cs`、`CartLine.cs`、`PromotionComputationBudget.cs`；仅对与促销无关的卡支付类型做占位），对修复前后各跑一遍相同场景：

| 场景 | 修复前 | 修复后 | 说明 |
|---|---|---|---|
| 权重全为 1（A@12/B@6/C@6，applyQty=3，fixed=15） | 4.50 / 2.25 / 2.25 ✅ | 同左 ✅ | 既有行为未变，无回归 |
| **权重 2（W@12 weight=2，R@6，applyQty=3，fixed=15）** | 折扣 15.00、**应收 3.00** ❌ | 折扣 3.00、**应收 15.00** ✅ | **实测少收 12.00 元** |
| 跨 bundle 消费（W@10 weight=2，applyQty=1，fixed=8） | 4.00 ✅ | 同左 ✅ | 单单位 bundle 行为未变 |

修复后场景 2 的分摊结果（2.00 / 1.00）与 `PromotionEvaluationServiceTests` 的权威断言完全一致，两套引擎已对齐。

GitNexus `impact` 风险 LOW（影响面全在 `PosCartService.cs` 内部），`detect_changes` 确认 0 个执行流受影响。**CI 的 Windows 分片仍需跑一遍完整客户端测试。**

**遗留建议**: 让 `PosCartService` 复用 `PromotionEvaluationService` 的去重逻辑，或删除这套重复实现改为统一入口。两套同语义引擎并存本身就是缺陷来源（见 §7 中期项）。

### 1.6 卡支付本地仓储两个写入方法零守卫 [已复核]

**位置**: `apps/pos-wpf/src/Hbpos.Client.Wpf/Services/LocalCardPaymentAttemptRepository.cs:780`（`MarkOrderCompletedAsync`）、`:801`（`MarkAcknowledgedAsync`）

两者的 WHERE 子句都只有 `WHERE AttemptGuid = $AttemptGuid;`——无终态守卫、无主管结案守卫、无 `FinalizePending` 守卫、无版本 CAS，且 `ExecuteNonQueryAsync` 的影响行数被丢弃。

**关键对照（已验证）**:

- 带完整守卫的 `TryMarkOrderCompletedAsync`（同文件 `:1061`）**全仓零调用方**，是死代码
- 生产路径走的是无守卫版本：`CashPaymentWorkflowService.cs:3011`（OrderCompleted）、`:3116` 与 `:3264`（Acknowledged）
- 同仓 Square 对等实现（`LocalSquarePaymentAttemptRepository.cs:1863`）是先读、再调带 7 条守卫的 `TryMarkOrderCompletedAsync`、0 行则抛异常

**后果**（`MarkOrderCompletedAsync`）: 读取与写入之间跨了两跳 `Task.Run`，窗口内若主管结案把该行推进为 `FinalizePending + SUPERVISOR_CONFIRMED_NOT_PAID`，写入照样成功 → 同一行同时断言"订单已收钱"与"主管确认未扣款"，且 `RecoveryPhase` 停在 `FinalizePending`（本文件 6 处写入都排斥该值），该行进入任何代码都修不了的死锁状态，并持续被当作未结记录阻塞这台收银机。

**后果**（`MarkAcknowledgedAsync`）: 读取与写入之间隔了一次数秒的 Linkly 网络请求，典型 TOCTOU。窗口内该 attempt 若被推进为待复核状态，ack 照写 → 因多处查询都要求 `AcknowledgedAt IS NULL`，这笔结果未定的交易静默消失在恢复队列外。

**建议**: 把两个调用点改为调用带守卫的 `Try*` 版本并检查返回值。死代码 `TryMarkOrderCompletedAsync` 已经写好了，直接用。

## 2. 高优先级问题

### 2.1 Linkly 轮询遇 429 等未枚举状态码 → 在途交易判死且永不再核对 [已复核]

**位置**: `apps/pos-wpf/src/Hbpos.Api/Services/LinklyCloudBackendAsyncService.cs:2347`

`ApplyTransportResponse` 只枚举 200/202/408/5xx/401/403/404，其余一律 fallthrough 写成 `Status = Failed` + `IsActive = false`。而 `IsTransportRecoveryFailure`（`:2784`）只含 408 和 5xx，**429 不在其中**；此后 `ShouldRefreshOfficialTransaction` 恒为 false，不再向 Linkly 查真实结果。

**失败场景**: 顾客正在输密码时 Linkly Cloud 返回 429（限流，高峰期常见）→ 会话变 `Failed` → 客户端认定终态并向收银员报失败 → 终端其实已批准 → 收银员重刷 → **重复扣款**，且该会话永久停在 Failed 无法自愈。

**反证是疏漏**: 同文件 `ApplySendKeyTransportResponse:2427` 对 400 专门做了保守处理并注明"交易仍可能完成"；同样推理对只读 GET 更成立，却没有应用。测试只覆盖 408/500/599/401/404。

**建议**: 把未枚举状态码按"结果未知、保持 IsActive"处理，至少把 429 并入 `IsTransportRecoveryFailure`。

### 2.2 Square 仓储：带 token 的 checkout 绑定缺护栏 + 销售侧结案不吊销 token [已复核]

**位置**: `LocalSquarePaymentAttemptRepository.cs:1152`（`TryMarkCheckoutCreatedAsync`）、`:1268`（`ConfirmProcessed`）、`:1289`（`ConfirmNotProcessed`）

这条缺陷需要**两个独立疏漏同时成立**：

1. `TryMarkCheckoutCreatedAsync` 的 WHERE 只有 `AttemptGuid + SubmissionToken + Status IN (...)`，缺 `RecoveryPhase <> FinalizePending` 和主管结案码排除——而这两道护栏在同文件分别出现 37 次和 18 次，是标准模式
2. 销售侧主管结案（`ResolvePaymentWithJournalAsync`）清空了 `CheckoutId`、`CheckoutStatus`、`PaymentId`、`PaymentStatus` 等 7 个字段，**唯独不清 `SubmissionToken`**；而退款侧 `ResolveRefundCoreAsync` 的三个分支（`:1470`、`:1496`、`:1518`）全部清空

**失败场景**: Square checkout POST 卡住（这正是触发恢复的场景）→ 主管在异常中心结案 → POST 迟到返回并调用 `TryMarkCheckoutCreatedAsync` → token 仍有效、护栏又缺失 → UPDATE 生效，`Status` 被改回 `CheckoutCreated`、`UpdatedAt` 被顶掉。

- 对 `ConfirmProcessed`：后续 CAS 失败，主管已确认的"已收款"推不到 `OrderCompleted`

### 2.7 本地存储与云同步的高优先级问题 [代理报告，主审查者已复核前两条的核心事实]

**共享挂单被强制释放后，原终端的订单仍会落库 → 同一批货两张正式订单**
`SharedHeldOrderRepository.cs:1306` + `SharedHeldOrderService.cs:537`

真实触发路径是 force-release 而非"同时取单"：`ForceReleaseAsync` 只调 `ValidateClaimScope`（hold + 门店），**不调 `ValidateClaimOwner`**——跨设备强制释放正是它的用途。时序：A 机取单、claim Active、购物车已恢复 → A 掉线但继续收银 → 主管在 B 机强制释放（以为 A 崩了）→ hold 回到 `Pending` → B 取单卖出并拿下 Primary → A 恢复网络上传，服务端见 claim 已终态，只记 `Unmatched` 且**一个字都不改 hold 状态**，订单照常写入 `sales_order`。

`UX_..._Association_Primary` 只保证"一个 hold 恰好一个 Primary"，挡不住第二张 `sales_order`。A 侧无任何防护：`SharedHeldOrderPaymentSourceResolver` 只读本地 claim（离线时仍是 Active），不回服务端核验；WPF 完全不消费 `OrderSyncResponse.Disposition`，`Unmatched` 在收银台不可见。

注意：该行为被测试**显式固化**——`SharedHeldOrderRepositoryTests.cs:229` 断言关联后 hold 仍为 `Pending`。这是被编码进测试的设计缺口，不是疏漏，修复前需先确认原始意图。

**退货额度校验的 Serializable 被 NOLOCK 击穿 → 超额退款**
`OrderReturnService.cs:590`、`:696`、`:729`

与 §1.1 同源。`BeginSerializableTransactionAsync` 的保护来自读操作的范围锁，但校验全走 `db.Queryable<>` → `WITH(NOLOCK)` → 不取任何锁。同一原单两笔退款几乎同时到达，双方读到相同的"已退数量/金额"、互不阻塞，**都通过剩余额度校验**。`sales_return_record` 上只有非唯一索引，无约束兜底。对照：同事务内的共享挂单逻辑是手写 `WITH (UPDLOCK)` 绕开 SqlSugar 的，退货这条没绕。

**代金券订单首传失败即永久传不上去**
`StoreVoucherService.cs:710`、`:726` + `OrderSyncService.cs:136`

预占令牌生命周期 5 分钟，`GetAsync` 强制 `Status='pending' AND ExpiresAtUtc > now`；客户端重试时原样重发本地 `LocalPayments.Reference` 里的旧 token（`OrderUploadService.cs:143`），**无任何重新预占或续期**。首传真失败 → 5 分钟后重试必然抛 `Voucher reservation token is invalid or expired` → 之后每次重试同样失败，订单永远停在 Failed，POSM 收不到这笔销售，券余额也没扣。

**目录"最新版本"按插入序号排序 → 旧目录被当成最新下发**
`CatalogIndexCache.cs:1036`（另见 `:1094`、`:1203`）

`GetLatestSnapshot` 用 `SnapshotEntry.Sequence`（单调自增插入序号）判新旧，而 `TryAdmitLoadedSnapshotLocked` 给**任何**懒加载进来的历史快照分配全新更大的序号。同一函数的 descriptor 回退分支却按 `GeneratedAt` 排序——两条路径口径自相矛盾，足证 Sequence 排序非本意。

失败场景：重启后恢复 V_new（seq 1）→ 某台 iPad 请求旧版本触发懒加载 V_old（seq 2）→ 此后 `_entries` 一旦为空（20 分钟 TTL 或 `InvalidateStore`），stale 分支就把 **V_old 当作当前目录返回**，收银端按旧价格全量同步。`PruneExpiredSnapshots` 的 LKG 保护用同一套序号，于是永久保护 V_old、可能淘汰 V_new。审查代理已用临时 xUnit 用例**实跑复现**（`Hbpos.Api.Tests` 为 net9.0，本机可运行），验证后已删除该用例。

**快照磁盘 IO 在全局锁内执行 → 跨门店阻塞收银请求**
`CatalogIndexCache.cs:1055` + `CatalogSnapshotStore.cs:145`

`GetByVersion`/`GetLatestSnapshot` 在持有全局 `_snapshotGate` 期间同步调 `_snapshotStore.Load(...)`；而 `GzipCatalogSnapshotStore` 把 Save/Load/RefreshExpiration 全串行在自己的 `_gate` 上，`Save` 锁内对整份目录做**三遍全量**（gzip 写 → 全文件 SHA-256 重读 → 全量解压反序列化校验）。A 店后台刷新进 `Save`（大店数秒）时，**所有门店**的 `CreateFullLease`/`GetLatestSnapshot` 全部卡在 `_snapshotGate` 上，且是请求线程上的同步 `Monitor.Enter`，并发下载易拖成线程池饥饿。`RefreshExpiration` 是常态路径。锁序单向，不死锁，只长时间阻塞。

## 6. 已核查、未发现问题的方向

以下方向经专项核查确认健康，列出以明确本次审查的覆盖边界：

**金额与计算**
- 全项目 104 处 `Round` 调用中 101 处显式 `MidpointRounding.AwayFromZero`，其余 3 处均为非金额（下载进度百分比 ×2、重试抖动窗口 ×1）——**零处金额使用默认的银行家舍入**
- 分/元单位转换全链路一致，未发现混用；货币硬编码 `"AUD"`，零小数货币的 100 倍错误不可达
- 部分批准三条路径均 fail-closed，不会按批准额少记账
- 现金 5 分取整只作用于现金部分，未误用到卡支付；混合支付（现金+卡+券）的分配与剩余应收经多组手算验证自洽
- 整单折扣分摊由最后一行吸收余额，既不丢分也不重复
- 分期模块为"总额+首付+任意次补款"寄存模型，不存在期数拆分，无"最后一期吃余数"类缺陷

**并发与数据完整性**
- SQLite 配置 `journal_mode=WAL`、`busy_timeout=5000`、`Pooling=false`；两个 `CreateOrGet` 用 `BEGIN IMMEDIATE`
- txnRef / 幂等键无碰撞可能（SHA-256 Base32 + 服务端全历史唯一约束 + SERIALIZABLE/UPDLOCK）
- 重复扣款 / 二次 POST 在结构上不可能（所有 409 分支以 `return` 结束）
- `LocalOrders.OrderGuid` 为主键，并发重复落单失败关闭
- UI 重复点击有三层防护（`AsyncRelayCommand` 默认禁并发 + 同步置锁 + attempt 幂等键）

**安全**
- SQL 注入：全部 SQL 的用户值走 `SugarParameter`，非常量插值仅 4 处且都是异常消息文本
- 证书校验：全项目对 `ServerCertificateValidationCallback` 等零命中
- Square webhook 验签正确（HMAC-SHA256 + `FixedTimeEquals` + 密钥缺失时失败关闭）
- 卡号脱敏正确（`SanitizeCardNumber` 只返回 `****` + 后四位，并整体剔除 track2/cvv/token 字段）
- 路径遍历有白名单与完整文件名校验
- `appsettings` 中所有密钥位均为空串占位，真凭据经 `${...}` 从服务器 `.env` 注入
- CORS 未启用（默认最严格）；认证中间件顺序正确
- Data Protection 三套 ring 目录隔离，生产缺挂载路径时直接抛异常拒绝启动
- 审计上报强制请求体 StoreCode/DeviceCode 与认证 claim 相等

**远程维护（权限最高的路径）**
- 下载器实现达教科书水准：SHA256 + `CryptographicOperations.FixedTimeEquals` 定长比较 + 大小上限 + `checked` 防溢出 + 文件名路径遍历校验 + 临时文件 `CreateNew` + `finally` 清理
- `sc.exe` 使用 System32 绝对路径（防 PATH 劫持），自实现 Windows CRT 参数转义（正确处理引号与末尾反斜杠），密码不入日志，超时后 Kill 进程树

**WPF 运行时**
- 事件订阅与定时器全部配对退订；DI 无 `AddScoped`，不存在 Singleton 捕获 Scoped
- 跨线程全部正确 marshal（先 `CheckAccess()` 再 `InvokeAsync`）；全项目无同步 `Dispatcher.Invoke`
- 关闭路径无死锁（`Task.Run` 移出 Dispatcher + 全程 `ConfigureAwait(false)`）
- 转换器缓存有界，in-flight 字典所有路径有 `finally` 清理

**共享挂单并发（全仓最严谨的部分）**
- 服务端认领四层防护：条件化原子 UPDATE + 显式 `Revision` 乐观锁 CAS（claim 与 hold 必须同时成功，否则整体回滚）+ `Serializable` 事务 + `sp_getapplock`(hold 粒度) + `WITH (UPDLOCK)` + 两个 filtered unique index 硬兜底。进程内 `SemaphoreSlim` 只是加速器，多实例部署下正确性不依赖它——**"两台机器同时取同一张挂单"这条路已堵死**
- 客户端本地 fence 由 DB 分区唯一索引 + 状态机触发器强制，不只靠应用逻辑；取单/对账全程 fail-closed（服务端 Active 而本地无 durable 事实时拒绝恢复，绝不伪造）
- 结账原子性：订单头/行/支付/卡交易/SyncQueue/挂单来源/claim 完成/本地挂单消费**全部在同一个 SQLite 事务**内，claim 缺失时整单回滚（有专门测试）
- 旧库迁移"换名→建新表→全量复制→删旧表→重建索引触发器"整体在一个事务内，任一步失败旧表原样保留

**本地数据安全**
- 全仓 DELETE 逐条核对，均带 StoreCode/主键精确谓词；**不存在任何按时间清理 `LocalOrders`/`SyncQueue`/支付记录的代码**，"清理未同步订单导致丢失"不成立（本地销售数据只增不删）
- `TestSalesDataResetService` 的全表 DELETE 用静态白名单数组，且 UI 可见性与调用接线**双重 `#if DEBUG` 门控**，Release 不可达
- schema 迁移幂等：客户端 ALTER 前查 `PRAGMA table_info`、索引触发器一律 `IF NOT EXISTS`；服务端 `IF OBJECT_ID/COL_LENGTH/NOT EXISTS` 全覆盖 + `SET XACT_ABORT ON` + 启动 applock 防并发
- 实测证伪一个怀疑：Microsoft.Data.Sqlite 的无参 `BeginTransaction()` 发出的是 `BEGIN IMMEDIATE`，所有事务开始即持写锁，代码中显式 `deferred: false` 只是冗余
- 代金券双花：`ClaimInsideTransactionAsync` 是原子条件 UPDATE（`affectedRows != 1` 即抛），事务外的 `ConsumeAsync` 只是记账，漏执行不会双花

**目录缓存**
- 失效与在途构建的 generation CAS 同在临界区，有十余个用例覆盖；`InvalidateStore` 不动 `_snapshots`，stale 分支返回已固定快照，未发现窗口期返回空目录
- 增量 since 用 `>=` 闭区间不漏同刻记录；每日预构建固定用不实行夏令时的 Australia/Brisbane 且当前生产未启用；锁序单向无死锁

**工程质量**
- 分层纪律严格：ViewModels 中零 `HttpClient`/`SqliteConnection`/`SqlSugar`/文件 IO 直接调用
- 本地化：1,726 条资源的 key 与格式化占位符在中英文间**零偏差**
- 零 TODO/FIXME/HACK；被跳过的测试全部有明确环境原因，且 `DEVICE_ACTIVATION_*` 与 `LINKLY_LINE_*` 两个 SQL 集成测试在 `weekly_sql` job 中确有配置并有 TRX 失败关闭机制
- 时区实现：缓存 TTL 分级、查库失败不阻断订单上传、IANA/Windows 双时区 ID 兜底

### 9.8 推广前七项的修复记录（2026-09-21）

七项对应的 PR 见 9.3 表格最后一列。以下只记录与 9.3 建议不同的做法，以及修复时补充核实的事实。

**2.5-1（#269）**：按 9.3 的方向修复。补取小票时，HTTP、JSON 异常与非调用方的取消（业务窗口到期、收银员点"停止等待"）只结束补取，保留已拿到的批准或拒付；调用方自己的取消照常上抛。刷新结果只有在同一 SessionId、仍为终态、批准/拒付判定不变时才采纳。

**2.5-7（#270）**：采用受控结案，没有走官方 GET 对账，原因有二：

- 现有测试与 Web 端注释把"未知状态即使误写 ACK 也不能释放线路"固化为设计约束，对账失败或 Linkly 不再返回结果时仍然没有出口
- Web 后端调不到 Linkly，对账只能解开 API 侧的闸门

做法：

- ack 请求新增可选标记 `SupervisorResolved`。只有带标记、且会话仍非终态时，API 才写入 `SupervisorResolved` 终态；已有的 Linkly 终态保留，不带标记的 ack 行为不变
- 5 条管理 SQL 与 Web 端 3 个谓词加入该终态。付款闸门只挡"终态未确认"，主管结案必带确认时间，所以付款闸门没有改（与 9.3 的建议不同）
- 客户端按 attempt 上已落库的主管结案码决定是否带标记，断电后续跑与补发 ack 同样生效；迟到的 Linkly 最终通知仍可覆盖该标记
- 补充核实：启用线路管理时，第 5 条管理 SQL（操作租约，`RunStatusTestAsync`、`RunLogonTestAsync` 经 `ExecuteTerminalTestRequestAsync` 获取）也挡 POS 端的状态测试与登录测试，不只挡管理端操作
- 生产 `POSM_LinklyCloudBackendSession` 目前没有"非终态且已确认"的行，无需处理存量数据
- 上线须先 POS API 与 Web 后端，再客户端

### 9.9 #266 未包含项的排查（2026-09-22）

#266（3-07）的描述里列了几项同类路径未在该 PR 处理，已逐一排查，**均无缺陷**，不需要修复。排查由核验会话「§2.5 和 §3 中等问题验证」完成（按 main `4324e360f`），主审查者回源码抽查了下列关键位置，与结论一致。

**WPF：LocalIp 与 Cloud 直连的批准金额核验**

- 批准结果只有一个出口：两个客户端所有 `approved=true` 的结果都只能由各自的 `ToAuthorizationResult` 构造
- LocalIp（`LinklyTerminalClient.cs:1375`、`:1407` 两个重载）：成功时要求终端金额 `AmtPurchase` 与请求金额严格相等；金额为 0 只在失败分支允许
- Cloud 直连（`LinklyCloudTerminalClient.cs:822`）：成功必须带金额和终端引用，否则判结果未知；实时路径每次取得结果都经过 `MatchesSubmittedResponseIdentity`（`:447`、`:455`、`:471`、`:477`），"已完成且成功"时转入 `MatchesRecoveryIdentity` 按两位小数比对金额
- 恢复路径：把 `attempt.Amount` 交给终端比对，拿到结果后再由 `LocalAuthorizationMatchesAttempt`（`CardPaymentRecoveryService.cs:5012`）核对交易引用、类型与金额
- 存单金额：`draft.CardAmount` 与 `attempt.Amount` 在建 attempt 时来自同一个金额变量（`CashPaymentWorkflowService.cs` 约 2138、2149 行），仓储里没有任何 UPDATE 会改写二者，所以必然相等。本地路径没有像 3-07 的后端路径那样显式比对草稿金额，属于可选的防御性加固，不是缺陷
- 主管"确认已付款"须填银行证据或付款引用，对话框显示记录金额，属人工路径

**iPad 与手持端：同类问题（批准金额核验）比 WPF 更完整，共四层**

1. Linkly 适配器：`linkly-cloud-backend.ts` 映射为批准后必须经过 `buildApprovedCardSyncEvidence`（约 1197 行）；没有卡交易明细返回 `LINKLY_CARD_EVIDENCE_REQUIRED`，金额、TxnRef、会话号、批准码任一不符都降级为未知
2. Square 适配器：销售由 `verifyPayment`（`square-payment-adapter.ts:406`）比对 `approvedMoney ?? totalMoney`，退款比对 `amountMoney`，不符即降级为未知
3. 共享包 `@hb/pos-payments-core` 的 `protectedEvidenceForAttempt`（`payment-attempt-service.ts:939`）：任何批准的卡结果都必须带受保护证据，且 `amountCents` 等于 attempt 金额，否则存为未知
4. 存单：批准支付行的金额直接取 `payment_attempts.amount_cents`，不经草稿；迁移中的触发器要求消费行金额等于记录金额。iPad 恢复中心遇到因证据不足而降级的批准会标 `queryVerified=false`，不能人工补成已收款

手持端与 iPad 的差异仅在 iPad 独有的人工刷卡与恢复中心，核心金额比对两端相同。另外，#266 上线后，iPad 与手持端在 webhook 未送达时的 Linkly 批准也能拿到经核验的明细并自动恢复（此前 GET 证据的 TxnRef 被脱敏，约 85% 会降级为未知、转主管处理）。
